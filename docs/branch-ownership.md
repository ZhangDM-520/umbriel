# Branch ownership — the twelve branches this fork maintains

Standing contract for the pull requests this fork carries. The machine-readable copy of these rows and each branch's gate lives in the maintainer's warehouse, together with `branch-status.sh`, the probe that reads it; this file is the reviewable copy that travels with the integration branch. Update both in the same round.

Upstream squashes every pull request (`d3c85928 … (#585)`), so a branch here is a queue of commits, not a history: rebasing is lossless and a force-push costs nothing that upstream keeps.

## Conflict surface

Measured by `git merge-tree --write-tree` against every pair of the twelve: **54 clean of 66, twelve collisions.** Re-run the probe (`git merge-tree --write-tree` over every pair) before repeating a count claim — a clean pair today says nothing about a pair introduced tomorrow. A conflict is therefore always one of three shapes:

1. **Upstream drift in a shared header.** #715 lost an include block to this shape; a rebase removes it, and it does not come back once the branch's merge commits are gone.
2. **Upstream moved or redesigned the code the branch edits.** #570 hit the redesign form: upstream replaced `raiseTransientTree()` with `raiseInOrder()` + `collectTransientTree()`, and no textual union compiles. #742 hit the milder form: upstream `dc4de689` moved the close-snapshot purge after the layer-surface destruction, so the branch's three lines sit at a location that no longer exists. A rebase fixes both; neither is a `nightly` union.
3. **A sibling fork branch, never upstream.** Those belong to the `nightly` replay, where both sides exist, not to the PR branch.

The twelve collisions are six standing pairs and six from row 19's rewrite. Standing: `feat/resize-physics` against `floating-minimize-animation` (`animation.md`, `view_state.cpp`), `fix/drag-deform-settle-crop` (`view.cpp`/`view.h`/`view_animation.cpp`/`view_lifecycle.cpp`), `fix/ram-footprint` (`effect_registry.cpp`), `fix/resize-lag` (`view.cpp`/`view_state.cpp`) and `feat/scratchpad-restore-fade` (`animation.md`/`view.cpp`/`view_state.cpp`), plus `floating-minimize-animation` against `feat/scratchpad-restore-fade` (`animation.md`, `view.h`, `view_animation.cpp`). Row 19's rewrite adds `background-blur-protocol` (`overview.cpp`), `scratchpad-close-animation` (`scratchpad.h`), `feat/scratchpad-restore-fade` (`scratchpad.md`, `scratchpad.h`) and `feat/scratchpad-drop-adopt` (`scratchpad.md`, `scratchpad.cpp`, `scratchpad.h`). The drop-adoption branch inherits the restore fade's pairs because it is stacked on it; merging row 20 after row 18 keeps its base inside `nightly`, so only the row-19 files and its one `scratchpad.cpp` hunk against `feat/resize-physics` collide there.

`feat/resize-physics` was the last of the resize family to be cut and shares a file with almost all of them, which is why `nightly` carries it as C6 and merges it last in its group. Row 19 carries C10 for the same reason on the scratchpad side.

## Decision log

- **2026-11-19 · #715 · rebased, not resolved.** Six local merge commits made every upstream move a conflict in the branch's tree. Rebased onto `56b67604`; the include conflict became `#include <pixman.h>` + `#include <span>` in clang-format order. Three extra conflicts appeared that `merge-tree` had not predicted (rebase replays each commit rather than one three-way merge): `server.h` (a stale `wlr_image_description_v1_data` declaration the branch carried against upstream's `ColorDescription`), `popup.h` (`<list>` vs `<vector>`, both needed), `view_chrome.cpp` (the branch's inline presented-size predicate against upstream's `chromeContentSize()` — upstream's wins). One harness client commit conflicted in its comment block only; the duplicate frame-callback docs commit upstream already had was dropped by the replay. A latent defect surfaced only after the merge: `kAllowedSecurityContextGlobals` kept its old bound of 33 while the branch added a 34th entry, which the auto-merge had silently hidden. **Lesson: a clean `merge-tree` says nothing about whether the tree compiles.**

- **2026-11-19 · #733 · rebased clean, conflicts left for `nightly`.** 65 commits behind, zero conflicts. Its two remaining conflicts are with fork-only branches; repairing them on the PR branch would put fork-integration state into an upstream pull request.

- **2026-11-19 · #570 · rebase plus one reconciliation commit.** The three traversal refactor commits were dropped rather than resolved, because they rewrote the function upstream had already rewritten. Upstream's `raiseInOrder()` is the base; one walker now serves both the frame-collecting raise and the re-home; `applySceneParent()` returns whether the move left the drag tree and `syncTransientSceneParent()` is `bool` again. **A new behaviour had to be pinned:** upstream now re-syncs the previous focus in `Workspace::setFocusedView()`, which pulled a dialog riding a settling drag out of the drag tree and back into the workspace it was carried out of, and a switch then clipped it away mid-settle (`drag/settle_pinned_dialog`). A view the drag presentation owns now refuses the re-home. Falsified by neutering the guard, then stressed 16/16.

- **2026-11-19 · `fix/resize-lag` · unioned in `nightly`, not rebased.** Cut on `c89f6771`, so it meets every later member that shares its files. All four collisions are unions and two are duplicate code, not competing designs: `feat/resize-physics` had already extracted the branch's inline `Cursor::isResizingView()`/`resetMode()` guard into `View::cancelResizeGrab()`. The branch keeps its own work — the target-box presentation, the configure trace, the `unmap-client` delay/bufferless ack — and inherits the extracted helper. **No behaviour is re-decided**, which is why this is not a branch-owned conflict. A rebase was rejected: its two commits are a test commit and a fix commit that only build in sequence, and replaying them through four merged members would strand the intermediate tree unbuildable, the same trap #715 hit.

- **2026-11-21 · `feat/scratchpad-drop-adopt` · one union against `feat/resize-physics`, and neither half is unchecked.** Its `66e57486` routes "the pointer owns this view" through `isCarried()` in eight places, including two predicates in `scratchpad.cpp` that row 15 had taught to spare a resize grab as well. The branch never had a resize condition — it was on our side, from the merge — so the collision is a union, recorded as C11 in the manifest, and `isCarried()` was deliberately **not** widened: it is also the admission and restore guard, where a resize grab is cancelled rather than refused. **Both resize clauses are unobserved by the suite** — dropping either leaves `scratchpad/` fully green, and only `-Werror` catches the orphaned `cursor` local — while the drag clause is pinned by the branch's new `scratchpad/drag_pad_actions`. The gap is a `feat/resize-physics` follow-up: drive a usable-area change and a pad-definition reload from a resize grab.

- **2026-11-21 · #742 · stale, and the fix belongs on the branch.** Upstream `dc4de689` moved the close-snapshot purge out of `Server`'s output teardown to *after* the layer-surface destruction, because a snapshot's scene tree holds layer surfaces that point at the `wlr_output`. The branch adds three lines to that block in place, so `git merge-tree --write-tree upstream/main origin/scratchpad-close-animation` now conflicts. By the freshness rule the branch owns it: a rebase re-applies the three lines at the relocated site and the `nightly` union becomes a no-op. The rebuild stopped publication for this, carried the union so the rest could be measured, and recorded it as S1 rather than as a nightly resolution. **The branch went stale without changing: upstream moved under it.** Resolved the same day: the branch was rebased onto `60639b8f`, and its five commits now merge clean into `upstream/main` and into `nightly` with no union at all.

- **2026-11-21 · `fix/overview-scratchpad-fade` · rebuilt as one squashed commit, unioned as C10.** The review-round work arrived as a single commit cut on `c89f6771` rather than five commits on the previous base, so its diff no longer carries upstream reverts and it now collides with four earlier members. Every hunk is a union: the blur protocol's client region is kept and the pad's own alpha rule applied to it, `OverviewHidden` joins the tracked close snapshots, and the pad's user-facing sentence is the branch's. Two build-time traps came out of it: the union can re-insert a `visibleOn()` declaration the restore fade already makes, and `tools/remark/format.mjs` does nothing when given no file, so the table must be passed explicitly.

- **2026-11-21 · C10 falsification, honestly reported.** Both halves of the row-19 union are **unobserved** by the current checks. Pinning `card.blur.setAlpha(1.0F)` leaves `overview/scratchpad_blur` and `overview/scratchpad_transition` green, and forcing the client region empty leaves `protocol/background_blur` green; only the compiler notices the region is gone (`-Werror=unused-variable`). The union is still required for correctness — a pad card's blur must leave with it, and a client blur region must map into the card — so the follow-up belongs on the branch: pin the pad card's blur alpha mid-fade, and add an overview case to the background-blur check.

- **2026-11-20 · `feat/scratchpad-restore-fade` · unioned in `nightly`, not rebased.** Cut on `fix/resize-lag`, so it predates the minimize timeline; its `fadeEvent()` override met the minimize branch in `view_animation.cpp`, and its event-table rewrite met `windows_minimize`, `physics` and `blur_strength` in `animation.md`. All three collisions are unions of two accepted changes, and the branch merges into `upstream/main` cleanly, which is what settles who owns them. Its companion `fix/overview-scratchpad-fade` merged clean: the two touch disjoint functions of `ScratchpadManager`, and the `scratchpad.md` sentence both produced is identical. **A collision is judged against `upstream/main`: fresh means `nightly` unions it, stale means the owner fixes it.**

- **2026-11-21 · S2 · `feat/scratchpad-restore-fade` breaks `transient/modal_follow`.** Its second commit keeps an emptied pad visible by design. That pad covers its output, so a later pointer press lands on the pad instead of the workspace window behind it, and the check's Mod-drag moved nothing. Passes on `upstream/main`, passes on the previous nightly tip, fails at the replay's row-18 merge, passes again once the pad is closed before the pointer movers. **The branch's gate ran `animation/` and `scratchpad/`, never `transient/`; a behaviour change that removes a window from the pointer is a gate gap, not only a nightly collision.** The branch owns the choice: release the pointer when the pad holds no window, or close the pad in the check's mover. **Resolved the same day, and it took both halves.** `d29ba811` makes the dim rect's `accepts_input` follow the pad's contents (`hasVisibleEntriesOn()`, named `showsEntriesOn()` at the time), so an empty pad dims and blurs without swallowing a click and a window under it stays draggable; the same commit teaches `mover_overview_drop` to restore a parent the Mod-drag may now have dropped into that pad and to dismiss the pad before the card drop. `transient/modal_follow` is now part of this branch's gate and passes 16 of 16 stressed.

- **2026-11-21 · the fork runs no CI, by decision.** GitHub Actions is disabled on `ZhangDM-520/umbriel-nightly`: both the `gh workflow run` path and the raw dispatch endpoint answer HTTP 422 "Actions has been disabled for this repository", `allowed_actions` is `local_only`, and the fork's `pull_request` runs stopped after `bc10febd`. The owner ruled that repairing it is not worth an errand — this branch is rebuilt locally, is never proposed from the fork, and each member's own pull request carries the work to upstream's CI. **A claim about `nightly` is therefore a claim about a local run**: `just build`, the unit binaries, the harness over the touched areas, `just format-docs-check` and `clang-tidy` with the lint recipe's flags. `nightly` is not in the CI column of any row, and a missing fork run is not a pending check.

## Rules

- A fix goes on the branch that owns the surface, never on another branch and never on `nightly`.
- Rebase to sync with `upstream/main`; never merge. Merge commits are what turned #715 and #570 into conflicts.
- Force-push only with `--force-with-lease`, and only after showing the owner the diff and the gate results.
- `nightly` is rebuilt on `upstream/main`, never appended across a base move. Appending rows to an unmoved base is allowed at the owner's decision and is recorded in the manifest, which is the record of integration order.
- Conflict ownership is decided by `upstream/main`, not by `nightly`. `git merge-tree --write-tree upstream/main <branch>`: clean means the branch is fresh, and the collision it makes inside `nightly` is `nightly`'s to union; colliding means it is stale, and the fix belongs to its owner.
- Never `git add -A` in `~/Projects/umbriel-dev`; stage explicit paths.
- This file lives on `nightly` only and is never proposed upstream. A rebuild starts from `upstream/main`, so the bookkeeping commit that writes this file and `docs/nightly-manifest.md` must run after every replay.
